# Quickstart

From an empty directory to a passing test on Icarus Verilog. The steps below
take about ten minutes, most of which is the first Cargo build.

## 1. Prerequisites

| Tool | Version | Why |
|---|---|---|
| Rust | stable | the testbench and the harness are Rust |
| Icarus Verilog | 11 or newer; CI uses the Ubuntu 24.04 package, 12.0 | the simulator for this walkthrough |

Check both:

```sh
cargo --version
iverilog -V | head -1
```

## 2. Build the `rivet` command

```sh
git clone https://github.com/A-Ravioli/rivet
cd rivet
cargo build -p rivet-cli
```

That writes `target/debug/rivet`. Put it on your `PATH`, or use the full
path in the commands below.

## 3. Scaffold a crate

```sh
cd /tmp
rivet new counter-tb
```

`rivet new` prints where it wrote the crate and what to do next:

```text
rivet: created /tmp/counter-tb
rivet: next: cd counter-tb && rivet run --sim icarus
```

It refuses to write into a directory that already has a `Cargo.toml`. If you
built the CLI from a checkout rather than installing a published crate, pass
`--path` so the generated `Cargo.toml` depends on that checkout instead of
crates.io:

```sh
rivet new counter-tb --path /path/to/rivet
```

The crate it writes:

```text
counter-tb/
├── Cargo.toml          cdylib + rlib, a Verilator bin, a harness test target
├── rivet.toml          the design: top level, sources, per-simulator flags
├── build.rs            compiles the design with Verilator when that feature is on
├── hdl/counter.sv      an 8-bit counter with enable and synchronous load
├── src/lib.rs          two tests
├── src/main.rs         the Verilator entry point
├── tests/sim.rs        the `cargo test` entry point
├── .cargo/config.toml  the macOS link flags a VPI plugin needs
├── .gitignore
└── README.md
```

### `rivet.toml`

```toml
[design]
top = "counter"
sources = ["hdl/counter.sv"]

[design.params]
WIDTH = "8"

[sim.icarus]
args = ["-g2012"]

[sim.verilator]
trace = true
```

`[design.params]` values are strings, whatever the HDL type. They are passed
to the HDL compiler, so changing one rebuilds the design.

### `Cargo.toml`

The generated manifest names its backend with a Cargo feature, because one
library cannot carry two of them:

```toml
[features]
default = ["vpi"]
# One backend per simulator: VPI for Icarus and GHDL, VHPI for NVC. A
# library carrying both fails to load on NVC, which resolves eagerly.
vpi = ["rivet/vpi"]
vhpi = ["rivet/vhpi"]
verilator = ["rivet/verilator"]
```

### `src/lib.rs`

```rust
//! Generated by `rivet new`. Run it with `rivet run --sim icarus`.

use rivet::prelude::*;

/// Hold reset for two clocks, then release it on an edge.
async fn reset(dut: &Module, clk: Signal) -> rivet::Result<()> {
    let rst_n = dut.signal("rst_n")?;
    rst_n.set(0);
    dut.signal("en")?.set(0);
    dut.signal("load")?.set(0);
    dut.signal("d")?.set(0);
    clk.rising_edge().await;
    clk.rising_edge().await;
    rst_n.set(1);
    clk.rising_edge().await;
    Ok(())
}

#[rivet::test(timeout = 100.us())]
async fn counts_when_enabled(dut: Module) -> rivet::Result<()> {
    let clk = dut.signal("clk")?;
    let _clock = Clock::start(clk, 10.ns());
    reset(&dut, clk).await?;

    let count = dut.signal("count")?;
    dut.signal("en")?.set(1);
    for i in 1..=20u64 {
        clk.rising_edge().await;
        // The edge returns before the flop updates; read after it settles.
        read_only().await;
        assert_eq!(count.get_u64()?, i, "cycle {i}");
        next_time_step().await;
    }
    info!("counted to 20 by {}ns", rivet::now_in(rivet::Unit::Ns));
    Ok(())
}
```

The second generated test, `load_overrides_count`, drives a random value
through the load port using `rivet::rng()`.

### `build.rs`, `src/main.rs`, `tests/sim.rs`

```rust
// build.rs
fn main() {
    // Only the Verilator flow compiles the design into this crate.
    if std::env::var_os("CARGO_FEATURE_VERILATOR").is_some() {
        rivet_verilator::Build::from_manifest().build();
    }
}
```

```rust
//! src/main.rs: Verilator entry point; `build.rs` links the compiled model in.

// Link the test library so its `#[rivet::test]` registrations are present.
use counter_tb as _;

fn main() {
    rivet::verilator::main()
}
```

```rust
//! tests/sim.rs: `cargo test` entry point; see `rivet::harness`.
use counter_tb as _;

fn main() -> std::process::ExitCode {
    rivet::harness::main()
}
```

The `use <crate> as _;` line matters. The test registrations live in the
library, and without that line the linker drops them, so the binary runs zero
tests.

## 4. Run

```sh
cd counter-tb
rivet run --sim icarus
```

`rivet run` builds the library with Cargo, compiles `hdl/counter.sv` with
`iverilog` into `sim_build/icarus/counter.vvp`, copies the `cdylib` next to
it as a VPI plugin, and runs `vvp` with the plugin loaded.

The output has this shape. Times, seeds and the temporary path will differ.

```text

           0ns INFO  rivet_core::test         running 2 test(s) on icarus Icarus Verilog 12.0 (stable) (seed 7318782485113623909)
           0ns INFO  rivet_core::test         running counter_tb::counts_when_enabled (1/2, seed 11038368336460317929)
         250ns INFO  counter_tb               counted to 20 by 250ns
```

the run itself could not be set up.

## 5. What the run left behind

```text
sim_build/icarus/
├── counter.vvp            the compiled design
├── counter_tb.vpi         the harness, copied from target/debug/
├── build.hash             the content hash that skips the next recompile
├── results.xml            JUnit, the format cocotb writes
├── results.json           the same results, read back by `rivet run -j N`
└── logs/
    ├── counter_tb__counts_when_enabled.log
    └── counter_tb__load_overrides_count.log
```

## 6. Next steps

```sh
rivet run --sim icarus --filter load       # tests matching this regular expression
rivet run --sim icarus --waves             # sim_build/icarus/counter.fst
rivet run --sim icarus --waves --wave-open # and open it in surfer or gtkwave
rivet run --sim icarus --seed 42           # replay a specific seed
rivet run --sim icarus --shuffle           # shuffle the order, replayable from the seed
rivet run --sim icarus --log debug         # more log detail
rivet watch --sim icarus                   # rerun on every source change
cargo test                                 # the same tests through the cargo harness
cargo nextest run                          # one simulator process per test
```

`cargo test` uses the `RIVET_SIM` environment variable to choose the
simulator, defaulting to `icarus`, and `cargo test -- --list` lists the tests
without needing a simulator at all.

For Verilator, add the feature-gated build:

```sh
rivet run --sim verilator
```

which uses `build.rs` to compile the design into a native binary. See
[Simulators](simulators.md) for the prerequisites of each simulator, and
[VHDL](vhdl.md) for GHDL and NVC.

## 7. How long the loop takes

The number that matters day to day is not the simulation rate but the time
from saving a file to seeing a result. Measured by `ci/loop-latency.py` on
`examples/dff` with one test selected, so it is the loop and not the suite:

| Edit | Icarus | Verilator |
|---|---|---|
| nothing changed | 0.1 s | 0.1 s |
| one line in the test crate | 0.4 s | 0.6 s |
| one line in the HDL | 0.4 s | 12.5 s |
| everything, from clean | 0.8 s | 13.0 s |

The Rust rebuild is not the cost it looks like: a test-only edit is under a
second on both, because Cargo rebuilds one small crate and relinks. The
twelve seconds is Verilator compiling the design again after an HDL edit,
which is Verilator's own work. Python has no compile step, so cocotb's
test-edit loop is shorter than 0.4 s; that gap is a fraction of a second.

`rivet watch --sim icarus` keeps the loop to these numbers without retyping
the command. Reproduce with:

```sh
ci/loop-latency.py --sim icarus --example dff --filter counter
ci/loop-latency.py --sim verilator --example dff --filter counter
```
